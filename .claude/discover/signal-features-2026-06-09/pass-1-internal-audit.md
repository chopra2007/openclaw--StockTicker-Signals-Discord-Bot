## STEP 3 — Architecture Pushback

Ordered high → low severity.

### 1. The TWO unreconciled scorers — additive cross_reference sum vs engine precision escalation; the user reads the un-reconciled sum
**Severity:** high

**Claim:** The number printed in the alert headline is the additive xref total, but the buy/skip decision is made by a completely separate precision engine that the headline never reflects. A signal the precision engine quietly demoted to WATCHLIST (or that fired only on a HIGH-conviction cooldown bypass) still shows the inflated xref sum in the title. The two scores are computed from different inputs and never merged, so the retail trader anchors on a confidence number that did NOT gate the alert. This is the single worst precision leak: it makes weak alerts LOOK strong. It also means every per-source weighting fix you make to the xref sum changes the displayed number without changing whether the alert fires — the lever the user trusts and the lever that decides are different objects.

**Evidence:** discord.py:447 title `Cross-Reference: ${xref.ticker} | Score: {total}` uses the additive sum; the deciding class is a separate field at discord.py:398 `Precision Engine | score=p_score`; main.py:1269-1273 logs `precision=%s overrides xref_score=%.1f` — precision decides, xref is the number shown; engine.py:243-277 `_classify` runs on the engine total, not the xref total

**Concrete alternative:** Collapse to ONE score. Make `engine.analyze_signal` the single source of truth: feed the xref ScoreBreakdown components INTO the precision engine as features, output one calibrated number, and render that one number in both the headline and the decision. Concretely: in main.py:1255-1290, stop printing `xref.final_score`; print the precision engine's score and class together, and delete the standalone xref headline in discord.py:447. If you must keep two passes for latency, reconcile at the end: `final = min(xref_total, precision_total)` (precision-over-recall: the lower, gated number wins) so the displayed number can never exceed the gated one.

### 2. DEAD A1 contradiction penalty — contradiction_index never computed, always 0.0
**Severity:** high

**Claim:** The one mechanism explicitly built to catch the user's stated need — 'surfacing source contradictions before I act' — never fires. It is dead in TWO places, not one. The engine pass runs `_classify` with `contradiction_index=0.0` default. The 'post-process re-apply with the real value from xref' at main.py:1281 reads `xref.contradiction_index`, but cross_reference.py never assigns that field anywhere (grep returns zero hits), so it stays at its models.py default of 0.0. The STRONG->WATCHLIST downgrade at engine.py:265 and main.py:1284 is structurally unreachable. A ticker with three bullish analysts and a bearish YouTube consensus + bearish options flow sails through as STRONG with no penalty.

**Evidence:** cross_reference.py never sets contradiction_index (grep `contradiction_index` consensus_engine/cross_reference.py returns nothing); models.py:293 default 0.0; engine.py:233/289 param default 0.0; main.py:1281 `real_ci = float(getattr(xref, 'contradiction_index', 0.0) or 0.0)` reads an always-absent field; the only real computation is in analysis/_deprecated/regime_detector.py

**Concrete alternative:** Compute the index live in cross_reference.score_ticker, where every directional source already lands. Concrete formula: collect the signed direction of each contributing source (analysts, youtube consensus_dir, options flow sentiment, sec buy/sell), weight by points contributed, then `contradiction_index = min(opposing_weight, supporting_weight) / total_weight` (0=unanimous, ~0.5=evenly split). Assign it to `result.contradiction_index` before return. Then the existing main.py:1281 post-process and discord.py:417 bar both light up for free — the plumbing already exists, only the producer is missing.

### 3. ABSENT reliability engine — dead render path; reliability_decision/weights never populated
**Severity:** high

**Claim:** The entire user-facing risk-context block — Signal Verdict, the contradiction bar, source freshness, top drivers, and the invalidation condition — is gated behind `if xref.reliability_decision:` which is never truthy because no reliability engine exists to set it. So the contradiction bar the user wants is rendered ONLY inside a block that never executes, compounding the dead-A1 problem. The trader gets a score with no freshness, no driver attribution, and no invalidation level — exactly the context that separates an actionable setup from noise. `find -name reliability*.py` returns nothing.

**Evidence:** discord.py:402 `if xref.reliability_decision:` gates the whole verdict/contradiction/freshness/Risk-Factors block; reliability_decision defaults to '' and is set nowhere; discord.py:415-417 contradiction bar lives inside that dead block; no reliability:*.py file and no `reliability:` YAML block exist (pass-0 §4, §6.2)

**Concrete alternative:** Don't build a heavy reliability subsystem. Populate the three fields the render path already wants from data you already have: (a) `reliability_weights` = per-source recency in minutes (you have `extracted_at` on youtube mentions, news timestamps, options staleness gate) -> freshness label; (b) `reliability_decision` = a 3-way verdict derived from the reconciled single score + contradiction_index (CONFIRM / MIXED / CAUTION); (c) drivers = the top-2 ScoreBreakdown components by points. This lights up the existing discord.py:402-424 block with ~30 lines in cross_reference.py and zero new modules.

### 4. Unsigned YouTube boost — bearish YT consensus RAISES the score
**Severity:** high

**Claim:** A bearish YouTube consensus adds the SAME positive points as a bullish one. `score_boost` is set unsigned at cross_reference.py:371 and the sign-flip is gated behind `features.youtube_score.direction_aware`, which defaults False. So a flood of bearish videos on a ticker a watched analyst is long pushes the score UP toward STRONG. This directly manufactures false-positive bullish alerts and is the opposite of the user's 'kill signals that feel strong but underperform' goal. recency_decay, channel_reliability, and level_confluence are all OFF too, so a 20-day-old mention from an unregistered channel weighs identically to a fresh trusted one.

**Evidence:** cross_reference.py:371 `score_boost = conv_map.get(top_conviction, 10)` (unsigned); cross_reference.py:383-385 sign flip gated on `features.youtube_score.direction_aware`; consensus.yaml:745 `direction_aware: false` (also recency_decay/channel_reliability/level_confluence all false at :746-748)

**Concrete alternative:** Flip the four `youtube_score` flags ON in consensus.yaml:745-748. The code is already written and byte-identical when off, so this is a config-only change: direction_aware makes a bearish consensus subtract, recency_decay down-weights stale mentions, channel_reliability scales by trust. Verify with one live !all on a ticker with a known bearish YT consensus and confirm youtube_pts goes negative. Kill-switch metric: if STRONG-alert count drops >40% with no precision gain after a week, revisit the conviction map magnitudes.

### 5. 6h cooldown + per-analyst scaling — throttles new/good analysts identically to mediocre ones
**Severity:** medium

**Claim:** The scaling formula treats unknowns and median performers the same and throttles the very analysts the user most wants to hear from early. weight = clamp(precision*2, 0.5, 2.0); cooldown = base/weight. A 50%-precision analyst gets the full 6h. Critically, BOTH cold-start AND any analyst with fewer than 5 samples resolve to precision=None -> weight=1.0 -> full 6h baseline. So a brand-new high-signal analyst is silenced exactly as hard as a coin-flip one until they accumulate 5 graded outcomes. The bypass is keyed only to base_score>=30, not to analyst quality, so a low-quality analyst shouting a high-conviction tweet bypasses entirely while a measured high-quality analyst waits 6h. This suppresses the early, pre-mainstream signal the user explicitly prioritizes.

**Evidence:** db.py:1147-1156 `weight = min(2.0, max(0.5, precision*2.0))`, `cooldown_h = min(max_cap, cooldown_hours/weight)`; db.py:1149-1151 `precision is None -> weight = 1.0` (comment at db.py confirms cold-start AND sample_count<5 both arrive as None); db.py:1140-1145 high_conviction_bypass keyed to base_score>=high_conviction_threshold (30), not analyst precision; consensus.yaml:366-370 per_analyst block

**Concrete alternative:** Cooldown should gate on DUPLICATE-of-same-thesis, not wall-clock per analyst. Replace the time-based per-analyst window with a content gate: suppress a re-alert only when ticker+direction+catalyst_type matches an alert in the last N hours (dedupe the thesis, not the analyst). For genuinely new tickers/directions from the same analyst, let them through. If you keep time-scaling, give cold-start analysts a SHORT default (e.g. floor_minutes=30) not the full 6h — an unproven analyst should be heard once and then graded, not pre-silenced. Touches db.check_alert_cooldown + a new thesis-hash column on alert_history.

### 6. Inert min_base_score_for_alert knob (hardcoded >=20)
**Severity:** medium

**Claim:** The documented tuning lever for alert volume is a no-op. The Phase-1 gate hardcodes `quality_score >= 20` and never reads `alerts.min_base_score_for_alert`. The user (and any future tuner) believes editing consensus.yaml:363 raises the bar; it changes nothing. Worse, the only quality discount is a flat -5 for neutral direction, so the effective floor is base_score 20 (or 25 for neutral) regardless of config. This is a precision lever that is silently disconnected — the operator thinks they have a dial and they have a painted-on dial.

**Evidence:** main.py:1063-1066 `quality_score = tweet.base_score; if neutral: quality_score -= 5; return quality_score >= 20` (literal 20); grep `min_base_score_for_alert` across consensus_engine/ hits only _deprecated/regime_detector.py and the dead YAML key at consensus.yaml:363

**Concrete alternative:** One-line fix: `return quality_score >= cfg.get('alerts.min_base_score_for_alert', 20)` at main.py:1066. Reconnects the existing knob with zero new config. Then it becomes a real precision lever — raise to 25-30 to cut the weakest tweets out of the firehose without touching code.

### 7. Precision-engine thresholds (high 80 / medium 65, regime shift +/-5..10)
**Severity:** medium

**Claim:** The thresholds are applied to the WRONG number and the regime shift is too small to matter. _classify compares against the engine total, but the additive xref sum can reach 80 from soft sources alone — analysts(60) + social(35-cap) + trends(5) already overshoot 80 before any catalyst or technical confirmation. So 'STRONG' is achievable from crowd noise (3 analysts + Reddit + search interest) with zero hard catalyst. The regime shift only moves the STRONG cutoff by 5-10 points on a 0-100 scale that routinely runs hot, so in a panic regime (+10 -> cutoff 90) a noise-stacked signal can STILL clear. The thresholds assume a calibrated score; the score feeding them is an uncalibrated additive sum (retrain_enabled=false), so 80 means nothing consistent across tickers.
