That would escape the weekend pause, but it also keeps `await asyncio.gather(*tasks)` alive after `combined_stop` fires, so `run_live()` never returns to the weekend command-listener branch. Evidence: weekend branch is before live task construction in `consensus_engine/main.py:560-584`; `combined_stop` only tracks `stop_event|pause_event` at `main.py:628-636`; `gmail_watcher_loop(combined_stop, ...)` is inside the gathered task set at `main.py:649-677`. Fix: run the news watcher as a separate top-level supervisor, not inside the weekend-paused live scanner gather.

- Gmail scopes are still wrong for the existing label-based processing path. `SCOPES` are readonly + labels at `consensus_engine/scanners/gmail_watcher.py:26-29`, but `_mark_processed()` calls `users().messages().modify(...)` at `gmail_watcher.py:360-367`. The spec says the token has `gmail.modify`, but code does not request/verify it. Fix: switch to `gmail.modify`, force/recheck token consent, and verify a test label modify before enabling.

- #news alerts need a durable outbox before any live post. Existing Alfred already models this with `briefing_runs` (`db.py:369-379`) and `pending -> posted` flow (`consensus_engine/briefing/alfred.py:219-255`). The ad-hoc send helpers post directly to fixed channels (`alfred.py:166-190`, `main.py:720-729`, `scanners/youtube.py:100-111`). Fix: add `wolf_news_alerts(dedupe_key, status, discord_message_id, payload_json, created_at, posted_at)` and only post from a pending row.

**MAJOR**
- Do not assume existing Gemini video code is reusable for email chart images. `llm_client.py` is text-only OpenRouter/Groq chat payloads (`consensus_engine/llm_client.py:66-113`). The Gemini path is specialized around YouTube URLs via `types.Part.from_uri(... mime_type="video/*")` in `consensus_engine/analysis/gemini_video_parser.py:640-720`. Fix: build a small image-specific Gemini helper with image bytes/URI inputs, not a mutation of the video parser.

- The plan needs hard backpressure for chart vision. Current Gmail processing is serial per message (`gmail_watcher.py:205-356`), while the global Gemini limiter is 6 seconds per request (`consensus_engine/utils/rate_limiter.py:18-29`) and budgets are daily caps (`config/consensus.yaml:501-508`; `engine.py:50-130`). A 40-chart Wrap can stall the watcher or burn the day. Fix: cap images per email for v1, batch multiple images into one Gemini request where possible, and persist “skipped due budget/cap” telemetry.

- New DB schema cannot be “version 15” only. `init_db()` runs `SCHEMA`, column migrations, indices, then only inserts `_schema_versions` audit rows (`consensus_engine/db.py:735-778`). `_run_column_migrations()` is for adding columns to existing tables, not creating feature state (`db.py:641-730`). Fix: put new table DDL in `SCHEMA`, use `_run_column_migrations` only for altered existing tables, then add `(15, "...")`.

- Current Gmail message dedupe/marking semantics can lose or replay image-only emails. The watcher only records `seen_gmail_messages` after ticker inserts and hashes text body only (`gmail_watcher.py:277-356`). For Wolf, the signal may be in image URLs, not text. Fix: add a Wolf-specific processing table with message id, normalized HTML hash, ordered image URL hash, parse status, and error reason; mark Gmail processed only after durable state is written.

- Sector/asset scope is under-modeled if the plan leans on `sector_map.yaml`. That file maps ticker symbols to ETF buckets (`consensus_engine/data/sector_map.yaml:1-3`, `40-58`), while the product spec requires market, sector/group, asset-class, oil/gold/bonds/yields/BTC/dollar matching (`todo/wolf-macro-brain.md:45-46`). Fix: thesis schema needs `scope_type` + `scope_key`, not just ticker/sector ETF.

**MINOR**
- `_auth_results_pass()` uses the first `Authentication-Results` header and requires literal `dkim=pass`, `spf=pass`, and `dmarc=pass` (`gmail_watcher.py:140-154`). Real Gmail messages can contain multiple auth headers. Fix: evaluate all auth headers, prefer Google’s receiving header, and log/auth-fail sampled subjects before enforcing.

- Channel config is missing for #news. Current config only has `gmail_watcher.enabled: false` and Gmail paths/allowlist (`config/consensus.yaml:673-684`); existing send helpers target main alerts or Alfred briefing channels. Fix: add `news_alerts.enabled`, `news_alerts.channel_id`, `news_alerts.test_channel_id`, `news_alerts.allow_mentions`.

**SIMPLIFY**
- Cut v1 to: read one real Wolf email, extract HTML text + capped chart evidence, upsert one thesis table, post one deduped #news alert. Defer market-read/calls tables unless they are directly needed for the first alert. The product spec already says phase order is reader, stateful store, confluence, alerting, digest, beneficiary, backfill (`todo/wolf-macro-brain.md:91-108`).

- Do not implement key-level break monitoring in phase 1 unless it has a dedicated price watcher for Wolf levels. Existing level alerts only query `youtube_levels` (`main.py:731-738`). For v1, alert only on new/changed thesis from a new email; add level-break alerts after Wolf levels have a durable table and tested price source.

VERDICT: REVISE (must-fix: plan-file access, separate always-on news supervisor, gmail.modify verification, durable #news outbox/dedupe, Gemini image budget/backpressure)
