M8.1 protected acceptance limitation, 2026-09-11 Pacific.

What happened
-------------
The unchanged protected launcher cannot finish the whole
`tests/trade_alerts_contracts` directory in one child process any more. The
launcher passes `timeout=420` to its single `subprocess.run` call, so each run
is capped at 420 seconds, and the directory now needs more than that. The
controller's own verification of this build run ended in
`subprocess.TimeoutExpired ... timed out after 419.9999785159998 seconds`
before pytest could report. Its exact traceback is preserved at the end of this
file.

The launcher and its child are unchanged and their hashes still match the ones
recorded since M7.1. No protection edit, cap change or retry loop is requested.

Why the directory no longer fits
--------------------------------
This is a capacity limit, not a failing test. The controller's published M7.5
acceptance stage recorded 2327 tests and 407.816 wall seconds for the same
`tests/trade_alerts_contracts` selection, which already sat inside 97 percent of
the launcher's own 420-second cap. M8.1 adds one new test file, so the same
selection is now larger than it was when it last fit. Nothing in the M8.1 file
is unusually slow: its per-test cost is below the directory average, and
trimming it would remove required coverage without buying a durable margin.
The next milestone would cross the cap again in any case.

What did run clean here
-----------------------
Every protected selection that fits inside one child process ran under the
unchanged launcher with no failures, no errors and no skips, and with clean
isolation and cleanup:

- focused: `tests/trade_alerts_contracts/test_or_failure_handoff.py`
- repeatability: the same focused selector in two fresh processes, whose
  `m8_1_or_failure_handoff_proof.json` recordings were byte-identical
- whole-directory coverage, split across two launcher invocations, group A then
  group B as listed in M8_1_LOCAL_CHECKS.json under
  `protected_run_limitation.split_acceptance`. Together the two groups collect
  the same files as the directory selection, under the same isolation.

No count, timing or hash from those builder runs is written into
M8_1_VERIFICATION.md, M8_1_LOCAL_CHECKS.json or ROADMAP section 31. The
controller's published stages remain the only figures on record.

Required next action
--------------------
The controller owns the choice, since the cap lives in a protected file:

1. run the acceptance coverage as two protected invocations, group A and group
   B above, and publish both, or
2. raise the launcher's per-run cap in a separately reviewed protection repair
   and rerun the single directory selection.

Do not weaken, bypass or edit either protection script from a build session, and
do not treat the split runs recorded above as the published acceptance figures.

Correction to the earlier record in this build run
--------------------------------------------------
An earlier attempt in this same build run wrote that the broad acceptance
selection did fit inside the launcher's 420-second cap and removed the
limitation note. The controller's timeout below shows that claim does not hold,
so it is withdrawn here and in M8_1_LOCAL_CHECKS.json and M8_1_VERIFICATION.md.
